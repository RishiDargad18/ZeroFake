# Demo script

A rehearsed run of ZeroFake, roughly 8 minutes. Written to be read from a
second screen while you present.

The structure is deliberate: show what genuine looks like, catch a fake, then
show the system refusing to guess. That third act is the one people remember,
because almost nobody demonstrates a failure on purpose.

---

## Before you start

Everything runs on your machine. There is no public URL — if asked, the honest
answer is *"it deploys to a single VM behind nginx with TLS, the scripts are in
`deploy/`; I'm demonstrating locally."*

### Start the stack (about 5 minutes cold — do it 15 minutes early)

```bash
# 1. Fabric, in WSL
wsl -d Ubuntu
cd ~/hyperledger/fabric-samples/test-network
./network.sh up createChannel -c mychannel -ca

# 2. Chaincode (only after a fresh network up)

```

If that says 41/41, nothing can surprise you during the demo. Run it every

## Act 1 — A genuine product (3 minutes)

### 1. Log in as the manufacturer

> "Every role in the supply chain has an account. I'm signing in as a
> manufacturer, which is the only role allowed to create products and give them
> a blockchain identity."

### 2. Products → create a product

Fill in a name, code and brand. Submit.

> "The product now exists in the catalogue. Notice its blockchain status:
> **PENDING**. It exists on paper but has no identity on the ledger yet, and
> that distinction is the whole point of the system."

**Point at the QR code.** It was generated on creation and encodes the product's
UUID and nothing else.

> "The QR code is a pointer, not a proof. Anyone can photocopy it. Its only job
> is to tell us which identity to go and verify."

*Say this before anyone asks. It pre-empts the most common challenge.*

### 3. Register it on the blockchain

Open the product and register it. It takes two or three seconds — fill the
silence:

> "That's a real Fabric transaction being endorsed, ordered into a block and
> committed. Both organisations on my network have to endorse it before it
> commits."

Status becomes **REGISTERED**.

> "And notice I didn't do that second step. The blockchain service told the
> catalogue once the transaction committed — the browser isn't running that
> workflow, because if you closed the tab half way through you'd have a product
> on the ledger that the catalogue still thought was pending."

### 4. Blockchain page — the evidence

> "This is the local audit trail. That's the real Fabric transaction ID and the
> real block number it committed in. Nothing here is generated by my code — if
> the ledger didn't give us a value, we store null rather than inventing one."

### 5. Verify it

Verify Product → paste the product ID → **GENUINE**, risk 0, no rules triggered.

## Act 2 — Catching a counterfeit (2 minutes)

### 6. Verify a product that does not exist

Paste any random UUID, for example:

```
99999999-9999-9999-9999-999999999999
```

Result: **COUNTERFEIT**, risk 100, `PRODUCT_NOT_FOUND`.

> "No catalogue record at all, so there is nothing to check against the ledger.
> That's the easy case."

### 7. Explain the case that actually matters

You do not need to demo this; explaining it is stronger than a contrived setup.

> "The harder case is a counterfeiter who photographs a *genuine* QR code and
> reprints it. The ledger says that identity is real, because it is. What gives
> them away is that the genuine item is also being scanned — and one physical
> object cannot be in two cities at once, or be sold for the first time by five
> different people. That's what the duplicate-scan and multiple-location rules
> detect, and the blockchain is what makes that evidence trustworthy, because no
> single party can quietly edit it away."

If they want it demonstrated: log in as `customer@`, verify the same product from
a different location, and `DUPLICATE_QR` plus `MULTIPLE_LOCATION_SCAN` fire.

## Act 3 — The system refusing to guess (2 minutes)

**This is the part that wins the room.** Verified: the peer recovers on its own
in about five seconds, so this is safe to do live.

### 8. Kill the peer

```bash
wsl -d Ubuntu -e docker stop peer0.org1.example.com
```

### 9. Verify the genuine product again

Result: **502**, *"The blockchain service is unavailable, so authenticity cannot
be confirmed."*

> "The ledger is unreachable, so the system does not know. And it says so.
> It does **not** say counterfeit.
>
> That distinction is the most important decision in the project. If an outage
> made products look fake, you'd reject genuine stock every time the network
> hiccupped. A verdict is only ever returned when the system successfully
> established a fact — everything else is an error with its own status code."

### 10. Bring it back

```bash
wsl -d Ubuntu -e docker start peer0.org1.example.com
```

Wait about five seconds, verify again: **GENUINE**. The gRPC connection
re-establishes itself.

## Act 4 — Only if asked

**Ownership transfer.** Products → transfer to another user. Then Product
Timeline shows the full chain of custody read from the ledger.

> "The chaincode refuses this if the claimed current owner isn't the actual
> owner on the ledger. That check runs on every endorsing peer, so a compromised
> application server can't fake a transfer."

**Tests.**

```bash
cd services/zerofake-chaincode && go test ./contract/ -cover   # 82.6%
./scripts/smoke-test.sh                                        # 41/41
```

**Why blockchain and not a database?** See Part VIII of the interview guide.
Short version: no single party can rewrite it, and validation is enforced by
every peer rather than by your application server — then concede that you
operate both organisations yourself.

## If something breaks

| Symptom | Fix |
|---|---|
| Blockchain calls return 502 | `wsl -d Ubuntu -e docker ps` — is `peer0.org1.example.com` up? |
| A service is unhealthy | `docker compose logs <service> \| tail -30` |
| Frontend loads but calls fail | Check you are on **3001**, not 3000 |
| Everything is confused | `docker compose down && docker compose -f docker-compose.yml -f docker-compose.fabric.yml up -d` |

**If the demo dies completely**, do not debug in front of the room. Say:
*"I'll come back to the live system — let me walk you through the architecture
meanwhile,"* and switch to the diagram in the interview guide. You lose nothing;
panicking at a terminal loses a lot.

## Rehearse it three times

1. **Once slowly**, reading this file, to learn the click path.
2. **Once at speed**, timing yourself. Aim for 8 minutes with pauses for
   questions.
3. **Once with the script closed.** If you can't do it from memory, you don't
   know it well enough yet.

Things that only surface when you rehearse: the two-second wait during
blockchain registration is longer than it feels, copying a UUID between pages is
fiddly, and the sentence about the QR code being a pointer needs to land *before*
someone challenges you on it.

Start the stack fifteen minutes early. Every time.
